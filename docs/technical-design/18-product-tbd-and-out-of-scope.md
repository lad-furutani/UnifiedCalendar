## 18.1 初期版へ追加しないもの

予定編集、印刷/エクスポート、検索/絞り込み、重複統合、Push/Webhook、自動アップデート、右クリック、予定行drag、行件名copy、祝日取得、ネットワーク復帰event監視、常時最前面/AppBar/自動dock、help/tutorial、起動中設定file監視、詳細log level設定は実装しない。**通知は1.0.0では実装せず、1.1.0で予定開始前の通知だけを追加した（19章）。サウンド通知の設定、予定終了の通知、同期エラー/レート制限の通知、通知のクリック操作・スヌーズ・通知履歴は引き続き実装しない。**Microsoft共有calendarはOutlook予定表一覧へ追加済みで`/me/calendars`から列挙できるものまでとし、`/users/{owner}/...`による共有元メールボックス直接参照と未追加の共有・委任calendarの直接探索は初期版へ追加しない。

**本プロジェクトは Apache License 2.0 のもとで提供する。** 著作権者は `Logic and Design Inc.`。`LICENSE` をリポジトリのルートに置く。**`NOTICE` ファイルは作らない**（作ると再配布者全員に伝播義務が生じるだけで、得るものがない）。**ソースファイルへのライセンスヘッダー挿入も行わない**（Apache-2.0 附属書の雛形は推奨であって必須ではない）。

**Apache-2.0 を選んだ理由。** 商標条項（§6）が `UnifiedCalendar` と `Logic and Design Inc.` の名称を守る。署名付き製品として配布しているため、同名の非公式ビルドが出回ると問い合わせだけが当社へ来る。加えて特許条項と貢献条項（§5）があり、依存10件が既に Apache-2.0 なのでリポジトリ内でライセンスが揃う。**依存にコピーレフトが1件も無いため、選択に制約は無かった。**

**公開するのはソースのみとし、インストーラは社内で共有する（2026-09-08 決定）。** 公開先は `https://github.com/lad-furutani/UnifiedCalendar`。

**理由は同意済みユーザー数の上限である。** 公開ステータスが「本番環境（未検証）」のため、同意できるユーザー数に上限（100人とされる）がある（8.6）。**資格情報を埋め込んだインストーラを誰でもダウンロードできる状態にすると、社外の利用者が消費した分だけ社内の利用者が入れなくなる。** 上限は審査を通さない限り引き上げられない。あわせて、同意画面に出るサポートメールへ不特定多数から問い合わせが来ること、抽出した ClientId / Secret で当製品を名乗る別アプリを作られる余地があることも避ける。

**ソースを利用する者は自分の OAuth クライアントを用意する。** 配布バイナリ用の資格情報はリポジトリに含まれない（8.7）。その旨を README に記載している。

**公開リポジトリは新しい履歴で作る。** 開発時の作業指示（`handoff-*.md`）と受入記録（`acceptance-*.md`）、および Word 版の仕様書・技術設計書は公開しない。**削除では git 履歴から消えないため、現在のリポジトリは非公開のまま全履歴を保持し、公開側は公開対象だけで最初のコミットから作る。** 公開対象の選別は `prepare-publication.ps1` が行い、禁止ファイル名・資格情報の実値・個人パスを検査する。技術設計書から非公開文書への参照は残し、`docs/README.md` に注記を置く。

**GitHub Pages は同リポジトリの `docs/` から配信する**（`https://lad-furutani.github.io/UnifiedCalendar/`）。`github.com` は当社の所有ではなく Search Console で所有権を確認できないため、**Google の承認済みドメインには使えない**。`lad-furutani.github.io` を使い続ける必要がある。

### リポジトリ構成（2026-09-08 決定）

**3つのリポジトリを役割で分ける。同じ形のツリーを2つ持たない。**

| リポジトリ | 公開 | 中身 | 役割 |
| --- | --- | --- | --- |
| `UnifiedCalendar` | **公開** | src / tests / installer / ビルドスクリプト / docs（仕様書・技術設計書・Pages） | **唯一の作業場所。設計書はここが正である** |
| `UnifiedCalendar-work` | 非公開 | `docs/` のみ（指示書 `handoff-*.md` と受入手順書 `acceptance-*.md`） | 作業文書。**コードも設計書も置かない** |
| `UnifiedCalendar-archive` | 非公開 | 1.0.0 までの全履歴 | **凍結。参照専用** |

**ローカルの配置。** `work` の直下に `archive/` を置き、**`work/.gitignore` で `archive/` を除外する。** 旧リポジトリは自身の `.git` を保持したままなので、除外しないと入れ子のリポジトリとして中途半端に扱われる。**バックアップのため archive 自身にも非公開のリモートを持たせる。**

**`work` の中身を `docs/` だけにしたのは、公開リポジトリと形を違えるためである。** 同じ構造のツリーが2つあると、どちらが正か一目で分からず、編集先を取り違える。

**凍結した archive の `docs/technical-design/` と `specification.md` は、凍結時点の古い写しである。** 設計書の正は公開リポジトリ側にある。**実際に、公開ツリーを生成した後に本章へ加えた編集が公開側へ反映されず、移行時に取り込み直した。** 二重管理は必ずこの形でずれる。

**公開側へ非公開文書が混入しない仕組みが1つ失われた。** 公開ツリーを毎回生成していた間は `prepare-publication.ps1` が禁止ファイル名を検査していたが、**公開リポジトリで直接作業する方式ではその検査を通らない。** 代わりに**公開リポジトリの `.gitignore` で `docs/handoff-*`、`docs/acceptance-*`、`*.docx` を除外**し、置いてしまっても staging されないようにする。`prepare-publication.ps1` は役目を終えたため archive に残す。
